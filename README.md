# Panda Jobs — Angry Panda Heating and Cooling

Jobber-style web app (original code & branding) for Angry Panda Heating and Cooling,
Chicago, IL: Rigo creates clients, jobs and quotes/contracts; each client gets a
unique link (`#/c/<token>`) where they can review the quote, accept/decline
optional items, sign on screen, download their signed PDF, and later see job
status, the appointment, before/after photos and the completion summary.
On signing, the client automatically receives the signed PDF by email, with a
copy to angrypandahvac@gmail.com (live mode).

Spec: `~/workspace/angry-panda/panda-jobs-spec-2026-10-27.md`
Plan: `docs/superpowers/plans/2026-10-27-panda-jobs.md`

## Run it locally

```bash
cd panda-jobs
python3 -m http.server 8765
# owner panel:  http://localhost:8765/#/        (demo password: panda2026)
# client links: http://localhost:8765/#/c/<token>   (token shown in the owner panel)
```

No build step. All libraries are vendored in `assets/` (jsPDF, Supabase JS) —
there are **no runtime CDNs**.

## Demo mode vs live mode

`config.js` decides automatically:

- **Demo mode** (default, placeholder values in `config.js`): all data lives in
  the browser's `localStorage`; the full flow works end to end. The
  signed-copy email is **simulated** — it is logged in the job record as
  `demo — not sent`, nothing leaves the browser. Owner login is a demo gate
  (password `panda2026`, stored session in the browser).
- **Live mode**: fill in `SUPABASE_URL` and `SUPABASE_ANON_KEY` (the anon key
  is public by design) and the app talks to Supabase. Owner login becomes real
  Supabase Auth. Client portal reads go through the token-checked
  `get_job_by_token` RPC and signing through the `sign-and-email` Edge Function.

### Going live (deployment checklist — needs Rigo's accounts)

1. Create a free Supabase project (supabase.com) with Rigo's login.
2. SQL editor → run `supabase/schema.sql` (tables, storage bucket `job-photos`,
   RLS, RPC).
3. Create the owner user in Supabase Auth (email + password) — that becomes the
   panel login.
4. Set the function secret: `supabase secrets set GMAIL_APP_PASSWORD=...`
   (Gmail app password for angrypandahvac@gmail.com — generated by Rigo in his
   Google account with 2-Step Verification on; it lives ONLY as a secret).
5. `supabase functions deploy sign-and-email`
6. Upload documents bucket note: signed PDFs are generated in the browser and
   stored via the `documents` table / returned to the function; keep the
   `documents` storage bucket private.
7. Put the real values in `config.js`, publish the folder to GitHub Pages,
   activate Pages on the repo.
8. Re-run the full verification flow (see `docs/verification-2026-10-27.md`)
   against the live URLs before sending a link to a real client.

**Secrets rule:** the `service_role` key and the Gmail app password NEVER go
in this repo or the frontend — only Supabase secrets.

## Rules baked into the app

- A signed quote version is immutable: editing a signed job creates a new
  version that must be signed again; old signed versions stay intact with
  their own signature and timestamp.
- Email failure never loses a signature: the job is flagged
  `copy_email_failed` and the portal still offers the PDF download.
- Photos are compressed in the browser to max ~1600px before saving.
- Client-facing copy is English. The only credential claimed is
  "EPA Section 608 Universal Certified" — never "licensed/insured".
- The competitor price-reference table in the quote builder is owner-only
  internal reference data; it is never rendered in the client portal or PDF.
